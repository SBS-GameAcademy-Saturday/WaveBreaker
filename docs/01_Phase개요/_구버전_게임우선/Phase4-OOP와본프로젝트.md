## 🎯 목표

1. 클래스 · 상속 · 인터페이스를 **적을 만들면서** 배운다
2. 본 프로젝트를 개설하고 코어 루프를 완성한다
3. **네트워크 대비 설계 규칙 2가지를 몸에 심는다** (네트워크는 언급하지 않는다)

## 📚 다루는 내용

| 주제 | 이 게임에서의 형태 |
|---|---|
| 클래스와 인스턴스 | 스크립트 = 설계도, 씬의 오브젝트 = 실물 |
| 접근제한자 | `private` 기본, `[SerializeField]`를 쓰는 이유 (Phase 1의 약속 회수) |
| **상속** | `Enemy` → `ChargerEnemy` / `RangedEnemy` / `TankEnemy` |
| `virtual` / `override` | 적마다 다른 이동 방식 |
| **인터페이스** | `IDamageable` — 플레이어와 적이 모두 구현 |
| `enum` | 게임 상태(준비/전투/업그레이드/종료) |
| 매니저 패턴 | `GameManager`, `WaveManager` (싱글톤은 얕게 + 남용 경고) |

## 🔑 네트워크 대비 규칙 2가지 ★

이 Phase에서 **네트워크를 한마디도 하지 않고** 아래 두 규칙만 "좋은 코드 습관"으로 심는다.

| 규칙 | 학생에게 하는 설명 |
|---|---|
| **① 적 스폰과 체력 계산은 매니저 한 곳에서만 한다** | "여기저기서 적을 만들면 나중에 누가 만들었는지 못 찾아요" |
| **② 입력을 읽는 곳과 실제로 움직이는 곳을 분리한다** | "키보드 읽는 일이랑 움직이는 일은 다른 일이에요" |

> Phase 8에서 매니저에 `if (!IsServer) return;` 한 줄을 넣는 것으로 서버 권한 전환이 끝난다. **코드를 갈아엎지 않기 위한 포석이다.** 이 규칙을 안 심으면 Phase 8에서 전면 재작성이 필요해진다.

## ✅ 종료 조건

- [ ] `Enemy`를 상속한 적이 2종 이상 동작한다
- [ ] `IDamageable`로 플레이어와 적이 같은 방식으로 피해를 받는다
- [ ] 게임 시작 → 웨이브 스폰 → 전투 → 사망 → 게임오버가 **끊김 없이 한 바퀴 돈다**
- [ ] 적 스폰이 매니저 한 곳에서만 일어난다
- [ ] 입력 처리와 이동 처리가 분리돼 있다

> 재미없어도 된다. **한 바퀴 도는 것**이 유일한 기준이다.

## 🚨 위험 신호 (강사용)

| 신호 | 의미 | 대응 |
|---|---|---|
| **상속에서 반이 무너짐** | 정상. 첫 추상 개념 | 다이어그램 금지. **코드를 복사해서 부모로 올리는 과정을 실시간으로 보여준다** |
| "인터페이스 왜 써요? 상속으로 되는데" | 좋은 질문 | "적과 플레이어는 부모가 다른데 둘 다 맞아야 하잖아요" — 이 한 문장이면 된다 |
| 싱글톤을 남용하기 시작 | 위험 | `GameManager` 하나만 허용. "편해 보이지만 나중에 꼬입니다" |
| 056회차 프로젝트 개설에서 시간 소모 | 예방 가능 | 폴더 구조 + 에셋 패키지를 **강사가 만든 템플릿 프로젝트**로 배포 |
| 진도 격차 최대치 | 이 Phase에서 가장 벌어진다 | 스냅샷 배포를 **회차마다** 하는 것 고려 |

## ⏭ 연결

여기서 만든 `Enemy` 상속 구조와 `WaveManager`에 Phase 5가 콘텐츠를 얹는다. 규칙 ①②는 Phase 8에서 회수한다.
