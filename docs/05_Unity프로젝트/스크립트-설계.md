# 스크립트 설계 — WaveBreaker

> [확정-게임기획서.md](../00_기획/확정-게임기획서.md)를 코드 구조로 옮긴 문서. **강사 레퍼런스 프로젝트를 만들 때의 설계도.**
> 학생에게는 이 표 그대로 주지 않는다 — 회차마다 필요한 부분만 골격 코드로 가공해서 배포한다.

---

## 1. 설계 원칙 3가지

**① 네트워크 대비 규칙 2개를 처음부터 지킨다** (14주차에 "좋은 습관"으로 심는다)

| 규칙 | 코드에서의 의미 |
|---|---|
| **몬스터 스폰·체력 계산은 매니저 한 곳에서만** | `Instantiate(enemy)`가 `WaveManager` 밖에 존재하면 안 된다 |
| **입력 읽는 곳과 움직이는 곳을 분리** | `PlayerInput`(읽기)과 `PlayerController`(이동)를 나눈다 |

> 이 둘만 지키면 22~25주차에 `if (!IsServer) return;` 과 `if (!IsOwner) return;` 을 넣는 것으로 네트워크 전환이 끝난다.

**② 데이터는 ScriptableObject로 뺀다** (17주차)
수치가 코드에 박혀 있으면 밸런싱이 "코딩"이 된다. 데이터를 빼면 진도 느린 학생도 밸런싱에 참여할 수 있다.

**③ 상속은 몬스터에만 쓴다**
플레이어·무기까지 상속 계층을 만들면 노베이스가 길을 잃는다. 무기는 상속을 쓰되 **1단계까지만**.

## 2. 클래스 목록

### Player

| 클래스 | 책임 | 도입 |
|---|---|---|
| `PlayerInput` | 키 입력을 읽어 방향 값만 보관 | 14주차 (067) |
| `PlayerController` | `PlayerInput`의 값으로 이동 + 좌우 반전 | 14주차 (067) |
| `PlayerHealth` : `IDamageable` | 체력, 피격, 무적시간, 다운/부활 | 14주차 (070) — 무적시간은 080 |
| `PlayerLevel` | 경험치 누적, 레벨업 곡선, 레벨업 시 창 호출 | 17주차 (083) |
| `PlayerStats` | 업그레이드로 변하는 스탯(공격력·연사·속도·최대체력) | 18주차 |
| `WeaponHolder` | 보유 무기 목록 관리, 발사 요청 | 미정 (Phase 6 업그레이드에서 필요해지면) |

> 🔑 `PlayerInput` / `PlayerController` 분리가 규칙 ②다. 학생에게는 **"키보드 읽는 일과 움직이는 일은 다른 일"** 로만 설명한다.

### Weapon

| 클래스 | 책임 | 도입 |
|---|---|---|
| `MeleeRing` | 회전 축. 각도 분배로 칼을 배치하고 돌린다 | 16주차 (076·077) |
| `Blade` | 칼 한 자루. `OnTriggerStay2D` + 쿨다운으로 벤다 | 16주차 (076) |
| `AutoGun` | 사거리 안 가장 가까운 적을 찾아 코루틴으로 발사 | 16주차 (078·079) |
| `Projectile` | 이동, 충돌, 수명, **관통 카운트** | 16주차 (079) |
| `ExplosiveWeapon` | 착탄 지점 범위 피해 | 미정 (Phase 6 이후) |

> 🔑 `WeaponBase` 추상 클래스는 **만들지 않았다.** 무기가 두 개뿐이고 동작 방식이
> 전혀 달라(상시 회전 vs 쿨다운 발사) 공통으로 뽑을 코드가 없었다. 무기가 셋 이상
> 늘고 공통 코드가 실제로 생기면 그때 뽑는다.

### Enemy

| 클래스 | 책임 | 도입 |
|---|---|---|
| `Enemy` (abstract) : `IDamageable` | 체력, 피격, 사망 처리, `Attack()` virtual | 14주차 (070) |
| ├ `ChargerEnemy` | 플레이어를 향해 직진 · 부딪히면 큰 피해 (`Attack` override) | 14주차 (070) — 이동은 071 |
| ├ `RunnerEnemy` | 빠르지만 처음 방향으로만 직진 (`Move` override) | 15주차 (072) |
| ├ `RangedEnemy` | 일정 거리 유지 + 투사체 발사 | 16주차 |
| ├ `TankEnemy` | 느리고 단단함 — 받는 피해 절반 (`TakeDamage` override) | 15주차 (072) |
| └ `BossEnemy` | 크고 단단한 몬스터 + `isFinal` 이면 클리어 | 18주차 (090) — 패턴은 Phase 7 이후 |

**상속 구조 (학생에게 보여줄 형태)**

```
        IDamageable  ← 인터페이스
         ↑        ↑
   PlayerHealth  Enemy (abstract)
                  ↑    ↑     ↑     ↑
            Charger Ranged Tank  Boss
```

> 💬 6주차 콘솔 실습에서 만든 구조와 **똑같다.** 14주차 첫 회차에 그 코드를 다시 띄우고 "여기에 MonoBehaviour만 붙입니다"로 시작한다.

|---|---|---|---|

### Data (ScriptableObject) — 18주차 (087~089)

| 클래스 | 담는 것 | 에셋 개수 | 도입 |
|---|---|---|---|
| `EnemyData` | 이름, 체력, 공격력, 이동 속도, 색, 크기 | **6** (몬스터 3 + 보스 3) | 087·088·090 |
| `WeaponData` | 회전 칼 5개 값 + 자동 총 4개 값 | **1** (무기 둘이 공유) | 088 |
| `UpgradeData` | 종류(enum), 제목, 설명, 수치, 하한 | **8** | 089 |
| `WaveData` | 몬스터 종류별 수량, 스폰 간격, 동시 최대 수 | 미정 | 필요해지면 |

> 🔑 **SO 값은 "시작값" 이다.** 컴포넌트가 `Awake`/`Start` 에서 런타임 필드로 복사하고,
> 게임 중 업그레이드는 그 런타임 필드만 바꾼다. SO 를 직접 바꾸면 **Play 중 변경이 파일에 저장**돼
> 다음 판에도 강해진 채로 시작한다.

> 🔑 **전부 빼지 않는다.** 모든 종류가 쓰는 값만 SO 로 뺀다. 탱커의 `damageReduction`,
> 돌진형의 `chargeDamage`, 보스의 `isFinal` 은 그 컴포넌트에 남긴다.

## 3. 인터페이스

```csharp
public interface IDamageable
{
    void TakeDamage(int amount);
    bool IsAlive { get; }
}
```

> 💬 "몬스터랑 플레이어는 부모가 다른데 둘 다 맞아야 하잖아요" — 인터페이스를 설명하는 한 문장. 6주차에 이미 쓴 표현을 그대로 재사용한다.

## 6. 강사가 미리 검증할 것

- [ ] `WaveManager`의 스폰이 **정말 한 곳뿐인지** — 나중에 서버 전용으로 바꿀 지점
- [ ] `PlayerInput` → `PlayerController` 분리가 어색하지 않은지 (노베이스에게 설명 가능한 형태인가)
- [ ] `WeaponBase` 상속이 1단계를 넘지 않는지
- [ ] 풀링 도입 시 `WaveManager` 코드가 얼마나 바뀌는지 — 21주차 수업 분량 산정용
- [ ] 네트워크 전환 시 실제로 바뀌는 줄 수 — 위 "변경 목록"이 맞는지 직접 확인
